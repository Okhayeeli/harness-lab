# Evidence E-002 — /api/v1/* surface uniformly 404s on uninstalled instance

A later check does not change this record.

## Conditions
- Same instance as E-001 (gitea/gitea:1.22.3, digest sha256:76f516a1a8c27e8f8e9773639bf337c0176547a2d42a80843e3f2536787341c6)
- Install wizard still not completed
- No auth, no cookies, no token
- All requests from host loopback, same session, within seconds of each other

## Request
Seven paths, same invocation shape:
```
curl -s -o <body_file> \
     -w 'HTTP=%{http_code}  bytes=%{size_download}  ctype=%{content_type}' \
     --max-time 3 http://127.0.0.1:13172<PATH>
```
Paths probed:
`/api/v1/version`, `/api/v1/users/search`, `/api/v1/repos/search`,
`/api/v1/signing-key.gpg`, `/api/v1/nodeinfo`, `/api/healthz`, `/`.

All five `/api/v1/*` responses are **byte-identical** (same md5). That's not
"five 404s with similar messages" — it's the same exact response served for
every tested API v1 path.

Raw bodies saved under `evidence/probe_e002/body_*.raw` (at repo root).

## Target-state check
- `/api/healthz` answered `{"status":"pass"}` within the same probe pass → Gitea process is up, not crashed.
- `/` served ~22KB HTML → the HTTP front-door is live; the install UI is reachable (first bytes include `<html lang="en-US" data-theme="gitea-auto">`).
- Therefore the uniform 404 on `/api/v1/*` is routing policy, not failure.

## Limit
- Only these seven paths, only on this uninstalled instance.
- Only unauthenticated requests. A session cookie carrying install state could behave differently and was not tested.
- The content of the HTML served at `/` is a separate question (new thread THR-002).
- Does not establish what `/api/v1/*` does after installation completes.
